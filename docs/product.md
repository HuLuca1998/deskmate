# Deskmate 产品设计

2026-11-27 与用户讨论的结论。分三部分：用户明确定下的、默认采用但没被明确确认的、还没定的。
后两部分要改时直接问用户，不要当成定论。

## 背景

办公室有很多成员、很多设备，每个人的电脑上都装着自己的 codex 和 claude，登录的是各自的账号。
前身 acpp 是单机单人的面板，多人能力是后补的，而且所有功能都编译进后端，没法扩展。

核心洞察（用户原话的意思）：**每个人的 agent 带着这个人的技能、记忆和本地代码，同一个项目的同一个问题，在不同人的设备上问，答案不一样——离这件事越近的人，他的 agent 答得越准。** 所以别人的 agent 值得问，也值得派活。

## 用户明确定下的

1. **换架构重做**，不在 acpp 上改。
2. **不要中心服务器**，去中心化，局域网发现。
3. **无人远程**，所有人都在办公室局域网里。第一版不管跨网络。
4. **聊天不替换**，继续用 Discord。
5. **每个人有自己的 Discord bot**。
6. **不再隔离工作区**，每个人的电脑就是隔离区；agent 可以共享，前提是主人愿意开放。
7. **跨设备既要只读提问，也要能干活。**
8. **派活流程**：我 @ 某人的 bot 发布任务 → 那个 bot 自己建 issue → 通知它的主人处理。
9. **agent 先接**：agent 觉得任务很简单就自己做；有问题就问自己的主人。
10. **问主人后一直等**，不设超时。
11. **口头说的任务也必须整理成 issue 留存**，以便日后翻阅。
12. **要有插件设计**。
13. **只内部用**，名字用 Deskmate。
14. 用户列过的功能面：GitHub 登录、issue 通知推送、工作安排整理、个人助理（类似 OpenClaw 那类常驻、会主动找人的助理）。

## 默认采用，未被明确确认

这些是讨论中 Claude 提出、用户没有反对并沿着往下说的方案。

### 三条通道各管一种东西

| 通道 | 承载 | 特点 |
| --- | --- | --- |
| GitHub issue | 任务 | 有状态、留痕；对方关机也不丢，开机后接着处理 |
| 局域网直连 | 提问 | 即时、**只读**、问完即止 |
| Discord | 人和人聊天；bot 找主人、回链接 | 不变 |

「只读和干活都要」由此分开：**干活全部经 GitHub，直连通道永远只读。** 详见 [adr-001](adr-001-无中心对等架构.md)。

### 派活流程（细化）

1. 需求方在 Discord 里 @ 开发的 bot，说要做什么。
2. bot 背后的 agent 先分清这是**提问**还是**任务**：
   - 提问（「这个函数是干嘛的」）→ 直接只读回答，不建 issue。
   - 任务（「把登录页的报错文案改一下」）→ 往下走。分不清就反问一句。
3. 建 issue，指派给主人，在 Discord 回 issue 链接。不设确认步骤——公开 @ 并说了要做什么，意图已明确。
4. 通知主人有新任务。
5. agent 判断难度：
   - 简单 → 在独立工作树里开分支、改代码、**提 PR** 关联 issue，等主人审。
   - 拿不准 → 问主人，同时在 issue 下留言「已询问某某，等待答复」，然后一直等。
6. 有人直接在 GitHub 建 issue 并指派，走同一条流水线，从第 4 步开始。

### 护栏

- **「自己做」的终点是 PR，不是合并。** agent 对难度的判断是最不可靠的一环。只在独立工作树里动，不碰主人正在用的工作目录。
- **issue 作者是 bot 主人的账号**（bot 用主人的 GitHub 身份建）。正文必须写明由谁提出，并附 Discord 原消息链接。
- **等待状态要落库。** 关机、重启后没回答的问题必须还在并重新弹出。acpp 的教训：权限请求只存内存，丢一个整轮卡死。
- **各任务各等各的。** 等任务 A 的答复不堵任务 B。
- **多 bot 同服务器**：只有被 @ 或在自己开的子区里才回应。

### 跨设备提问

- 形状沿用 acpp 的 `/api/ask`：问题进、答案出。
- 每次问答在答方那边是一条可见会话，主人随时能翻。
- 设备互相发现时交换身份（GitHub 账号、Discord 账号、开放了哪些项目）。

## 待定问题

按「会不会卡住动工」排序。

### 动工前必须定

1. **插件设计。** 用户点名要，但还没展开。内核边界依赖它。已知的第一批插件样本：Discord bot、GitHub、局域网节点、个人助理。
2. **个人助理具体做什么。** 只说了「类似 OpenClaw」，没展开。合盖就下线这件事对它影响最大。
3. **app 打开后第一眼看到什么。** Claude 推测是「我自己的那部分」（我的助理、我的 issue 与待办、本机会话、等我批的请求），用户没确认。

### 可以边做边定

4. **谁可以给我的 bot 派活。** 建议两级：服务器里任何人都能让它建 issue 并通知我；只有我指定的人发的任务，agent 才自己动手。
5. **提问入口。** 人在 app 里主动选「问某某的 agent」，还是我的 agent 干活时自己判断该问谁，或者都要。后者需要设备广播自己开放了哪些项目。
6. **开放范围。** 建议按项目勾选，提问时工作目录固定在该项目内，避免记忆和其他项目的私人内容被答出去。
7. **答案带出处。** 建议回答里注明基于哪个分支、哪个提交——两个人的 agent 答案不同时才能判断谁对。
8. **额度。** 回答花的是主人的订阅额度，建议能按人限制每天次数。
9. **通知发到哪。** Discord 私信、app 系统通知，还是都发。
10. **斜杠命令重复。** 每个 bot 各自注册的话，输入 `/` 会看到每个 bot 一份。
11. **身份互验方式。** 设想是用 SSH 私钥签名、对 `github.com/<用户名>.keys` 验公钥，没验证过细节。

### 需要查证

12. **订阅条款。** 把个人的 Claude / ChatGPT 订阅额度给同事的请求用，是否符合各自的服务条款，没查过。
