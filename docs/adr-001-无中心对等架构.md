# ADR-001 无中心对等架构

- 日期：2026-11-27
- 状态：已定（用户决定不要中心服务器；通道划分为 Claude 提出、用户沿用）

## 决定

1. **没有中心服务器。** 每个人装同一个 app，所有节点对等，没有哪一个有特权。
2. **局域网发现**（mDNS）找到其他节点。无人远程，第一版不做跨网络。
3. **每人自带三样**：自己的 agent（本机 codex / claude）、自己的 Discord bot、自己的 GitHub 登录。
4. **三条通道各管一种东西**：任务走 GitHub issue，提问走局域网直连（只读），人和人聊天走 Discord。
5. **小内核 + 插件**：内核只管 agent 连接、会话、事件流、存储；Discord、GitHub、局域网、个人助理都是插件。

## 为什么不要服务器

Discord 和 GitHub 已经是现成的中心，自己再架一个是多余的。原来设想中服务器的每项职责都有去处：

| 职责 | 去处 |
| --- | --- |
| 人和人聊天 | Discord |
| 任务的事实来源 | GitHub issue 与看板 |
| issue 通知 | 每个 app 用自己的 GitHub 登录轮询（acpp 已验证，不需要公网回调地址） |
| GitHub 登录 | 设备码登录，不需要自己的服务端 |
| 找到其他设备 | 局域网发现 |
| 跨设备请求 | 设备直连 |
| Discord bot | 每人一个，各自的 app 挂着 |

对等结构让「我的电脑就是隔离区、我愿意才共享」直接成立：没有一处握着所有人的数据。

## 为什么干活不走直连

用户要求跨设备「只读和干活都要」。两种都走直连的话，直连通道就必须有一整套写权限的授权、审批、留痕机制，而且对方关机时任务会丢。

把任务放到 GitHub issue 上：

- 状态和记录天然有，用户本来就要求所有任务留成 issue。
- 对方不在线也不丢，开机后接着处理。
- agent 的产出是 PR，合并前有人审。
- 直连通道因此可以**永远只读**，安全规则简单到不需要逐次审批。

## 接受的代价

- **关机就离线。** 合盖后别人问不到你的 agent，你的 bot 不应答，助理不工作。任务不受影响（在 issue 上等着），提问会失败，此时如实告知对方不在线，退回到 Discord 问本人。
- **没有全局视图。** 谁在线、谁开放了什么，只能靠节点互相发现时交换，没有一处能看全貌。
- **远程用不了。** 以后有人远程，需要大家挂同一个 VPN，或另写 ADR 加中继。

## 对 acpp 教训的回应

- acpp 的 Discord 模块有 8900 行，是 ACP 核心（3400 行）的 2.6 倍，并且和后端焊死。这里 Discord 是插件，内核不认识它。
- acpp 的多租户、工作区隔离是在单机模型上后补的。这里隔离单位直接是一台电脑，不需要这一层。
