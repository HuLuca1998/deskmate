# ADR-002 技术栈

- 日期：2026-11-27
- 状态：方向已定；具体库待首个 spike 验证（见末尾）

## 决定

**全栈 TypeScript，Electron 桌面壳，官方 ACP SDK。** 不沿用 acpp 的 Go 后端。

| 层 | 选型 | 状态 |
| --- | --- | --- |
| 语言 | TypeScript（壳、内核、界面、插件同一种） | 已定 |
| 桌面壳 | Electron | 已定 |
| ACP 客户端 | 官方 `@agentclientprotocol/sdk` | 已定，client 侧接口待验证 |
| 界面 | React + Vite + shadcn/ui | 已定（沿用 acpp） |
| 存储 | SQLite | 已定，具体库待验证 |
| Discord | discord.js | 待验证 |
| GitHub | 设备码登录 + REST / GraphQL | 待验证 |
| 局域网发现 | mDNS | 待验证 |

## 为什么换掉 Go

1. **插件要能运行时加载。** 用户点名要插件设计。Go 没有可用的运行时插件机制，只能走子进程或 WASM，接口成本高。TypeScript 里插件就是一个模块，动态加载是语言自带的。这一条是决定性的。
2. **协议在快速变化，手写客户端追不上。** acpp 的 Go 客户端是手写的。2026-11 时 ACP 规范每周都在出新版本，v2 正在定型（规范已到 schema v1.35，SDK 2.12）。两个 adapter（codex-acp、claude-agent-acp）自己用的就是这个官方 SDK，它同时提供 v1 稳定版和 v2 实验版的入口。用它，协议升级基本是升依赖。
3. **一种语言贯穿全部。** 壳、内核、界面、插件都是 TypeScript，AI 协作者不用在两套规范、两套工具链之间切换。

## 为什么是 Electron

acpp 已经付过学费（acpp `docs/adr-015`）：WKWebView 在 macOS 拖动窗口缩放时卡顿严重，空白页也卡，是引擎固有问题，Tauri 用的是同一个引擎所以也救不了。Electron 体积大（.app 约 300MB），但这是唯一验证过可用的方案。

内核跑在 Electron 的 Node 侧，不再有独立的后端二进制，也就没有 acpp 那种「壳拉起后端子进程、壳和后端各一套 PATH」的问题。

## 放弃的东西

- **Go 单二进制**：部署简单、内存占用小。内部使用、每台都是开发机，这两点不重要。
- **acpp 的 Go 代码**：不搬。搬的是知识——两端 adapter 的协议实测结论、差异收敛思路、Discord 实测手法。

## 首个 spike 要验证的

动工的第一件事，不是搭完整骨架，而是用最少的代码把这几条跑通，跑不通就回来改本文：

1. 官方 SDK 的 client 侧能否完成与 codex-acp、claude-agent-acp 的握手、建会话、发一轮 prompt、收完事件流。
2. Electron 主进程里拉起 agent 子进程时的 PATH（acpp 的教训：GUI app 默认拿不到 Homebrew 路径）。
3. 一个插件模块能否在运行时被加载、拿到内核接口、卸载。
4. 两台机器在办公室局域网里用 mDNS 互相发现（部分办公网络会屏蔽组播）。

## adapter 版本策略

沿用 2026-11 对 acpp 的分析结论：上游一天发两三版，小版本里就有破坏性变更。app 记录「已验证的 adapter 版本」，只引导用户升到已验证版本，不追最新。
